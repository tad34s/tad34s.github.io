tdm

tdm is a dotfile manager I developed after being unsatisfied with the current solutions I found in the community. Since tdm does stuff differently than other dotfile managers (at least to the best of my knowledge), I feel the need to do a short writeup of my reasoning behind these decisions. I am currently using tdm as my dotfile manager, and I will continue to develop it to accommodate the needs of its users (which is only me, so my needs :P).

what is a dotfile manager

(skip this part if you already know what it is)

If you have ever configured anything related to programming, you might have encountered configuration files - basically text files where you write down the settings of the software you want to use. On UNIX-based systems, these files often start with a dot, since that makes the file (or directory) hidden, and a user won't see it unless they specifically enable its visibility.

We often care about our configurations and want to save them and distribute them to our other machines. This is the role of a dotfile manager1.

how other dotfile managers do things

Ideally, we would like to put our dotfiles into a version control system, most likely git. However, the files we care about are spread out across our system, and it is not feasible to turn our whole system into a git repository.

The way we normally get around this is by using symlinks2. A symlink is basically a normal file whose content is a path pointing to a file (or a directory) in a different location, something like a teleport. If a program expects a configuration file at ~/.config/fish/config.fish, we can create the actual file somewhere like ~/dotfiles/config.fish and create a symlink at ~/.config/fish/config.fish pointing to ~/dotfiles/config.fish. The program does not even notice, and when you open it yourself, you will be editing the original file.

Thus we can turn ~/dotfiles/ into a repository where only our important configurations are stored. This is the basic premise dotfile managers work on. Where dotfile managers help is in creating the symlinks for you. That is their main purpose.

GNU stow

One such program is GNU stow. Stow follows the UNIX philosophy of doing only one thing well. It takes what could be your dotfile directory and creates the symlinks for you. Stow basically looks at all the files in your dotfiles directory and creates a symlink for each of them under the home directory. For a file path such as ~/dotfiles/subdirectory/.zshrc, it creates a symlink to it at ~/subdirectory/.zshrc. This means that when you set up a new machine, you can just download the ~/dotfiles directory and run stow to set up your configurations. Stow works great as a simple tool. However, it has its issues.

It is not very ergonomic - adding config files to your dotfiles requires manually moving them to the repository and running stow again. It handles only files, although it can symlink a directory if all of the directory's children would have been linked, so you cannot add a whole directory and expect it to work when you create a new file in it. It also does not support having two versions of one dotfile inside the repository.

The last issue is the most important. It often happens that 90% of our setup on, for example, a notebook is the same as on a desktop, but it is important to us to maintain both configurations where they differ (like status bar settings, battery settings, etc.). Using the versioning system for this won't suffice, since this duplicates all the rest of the dotfiles, requiring constant git merging to keep them up to date.

chezmoi

Chezmoi is a dotfile manager I tried to use for quite some time. It is a well maintained piece of software that works great for some people, but for me it became pretty painful after a while. My main gripe with it is its solution to the problem of different setups. Instead of always symlinking, chezmoi allows you to define templates, where you leave spots for variables, for example, your cursor size, display resolution, etc. These variables are then set in the chezmoi configuration, which defines the values chezmoi should fill into those spots. The only problem is that it separates the configuration file from the file that is being maintained. This is because chezmoi maintains the template, and when you run the command, it fills in the variables and copies the result to the target location. Instead of a symlink, there is a whole new file, so when you edit this file, you are editing the copy, not the template. This leads to some frustrating scenarios. Either your changes get lost, or, since the copy is not part of version control, you simply forget about them, and your dotfiles become more and more disorganized. Additionally, since the variables are put inside a separate file, a person cannot maintain that file with git, or at least not in different versions, since that would put us in the exact same problem as before.

how tdm works

When I decided to start working on tdm, I wanted it to bring two main things:

  1. Adding whole directories to your dotfiles, automatically adopting their new children
  2. Fixing the problem of two versions of one file, while keeping all the necessary declarations inside the versioning system

The solution to problem 1 is relatively simple. When you add something to your dotfile repository using tdm, tdm checks whether it is a directory or a file. If it is a directory, tdm simply writes it down to remember it for later. Then, whenever you run a command that moves or updates dotfiles, it checks for new children in the directories it remembers, and if it finds any, it automatically adds them.

The second problem is much more interesting.

Fixing the two version problem

For a while, I wanted to make templates work by adding some method that would autonomously look at updates made to the rendered copy and bring them back to the maintained template. I then dropped the idea, since I never came up with anything I would be happy with. I decided on something else. I used forks.

First, in tdm you set up profiles. Think of them as different git branches, for example. Typically, you would have a profile for your desktop, a profile for your work laptop, a profile for your personal laptop, etc. When you create a new profile, tdm first assumes that everything should be the same as in the default profile. However, you can then decide to fork a file/directory managed by tdm. When you fork it, tdm creates a new copy of the file in the dotfile repo and changes the symlink to point to this new copy. Effectively, each profile is a list of different versions for a subset of the managed files/directories. What I did here is move from the per-line granularity enabled by templates to per-file granularity. This is the cost. However, it enables much better ergonomics, since all of the different versions of the file are now in version control, and when making changes to a file you know exactly where you are making them.

Here is an example. Say we have a waybar config at ~/.config/waybar/config.jsonc and we add it to tdm. The file is moved to the repo and a symlink is left in its place: 

$ tdm add ~/.config/waybar/config.jsonc

~
├── .config
│   └── waybar
│       └── config.jsonc -> ~/dotfiles/files/.config/waybar/config.jsonc
└── dotfiles
    ├── config.toml
    ├── files
    │   └── .config
    │       └── waybar
    │           └── config.jsonc
    └── forks

On the notebook, we switch to the notebook profile and fork the file. tdm copies it into forks/notebook/, and the symlink now points to the copy, which we can edit freely: 

$ tdm use notebook
$ tdm fork ~/.config/waybar/config.jsonc

~
├── .config
│   └── waybar
│       └── config.jsonc -> ~/dotfiles/forks/notebook/.config/waybar/config.jsonc
└── dotfiles
    ├── config.toml
    ├── files
    │   └── .config
    │       └── waybar
    │           └── config.jsonc
    └── forks
        └── notebook
            └── .config
                └── waybar
                    └── config.jsonc

The desktop profile has no fork of the file, so after switching to it, the symlink points back to the original version. Both versions stay in the repo: 

$ tdm use desktop

~
├── .config
│   └── waybar
│       └── config.jsonc -> ~/dotfiles/files/.config/waybar/config.jsonc
└── dotfiles
    ├── config.toml
    ├── files
    │   └── .config
    │       └── waybar
    │           └── config.jsonc
    └── forks
        └── notebook
            └── .config
                └── waybar
                    └── config.jsonc

I later realized that this setup does not rule out templates and could in fact empower them. While I am still thinking about implementing this, theoretically a template could simply generate each of the forked versions of the file. Updates to the forks would be kept, and the user would have to update the actual template only when they feel like it.

There are more quality of life features I have added to tdm. Overall, however, the two additions above have been absolutely amazing for me and have enabled an extremely smooth experience where I do not think much about my dotfile management other than remembering to commit my changes to git. I think this is a step in the right direction when it comes to dotfile managers.

quality of life with tdm

That was the main idea that got me working on tdm. In this section I will list quality of life things that I added to improve my personal experience with the software, in no particular order:

  1. You can clone a dotfile repository and deploy3 it in one command.
  2. When the user deploys and already has a file where tdm wants to put a symlink, tdm moves the file to its stash. When tdm ejects, it puts the original files back.
    • This allows the user to try someone else's dotfiles and then go back to their own without an issue.
  3. All the information necessary for deploying a repo is inside the repo. There is no need to create additional files with variables. Furthermore, this means that the differences are maintained in the repo.
  4. You can quickly switch between setups with only one command.
  5. tdm git - anything after this will be run as a git command inside the currently deployed dotfiles repo.
    • For example, in any directory you can run tdm git commit -m "committing changes to my dotfiles" and it will commit the changes in the dotfiles repository.
  6. tdm tree - to visualize all the symlinks tdm is making.
  7. include/exclude/include only/ignore per profile - per profile, the user can declare:
    • exclude - which files not to symlink
    • include - an override of exclude
    • include only - self-explanatory
    • ignore - which files to just ignore
    This is useful, for example, on my work laptop, where I want to symlink only the nvim configuration from my dotfiles.
  8. Kicking out files - when, for example, an ignored file is seen inside the dotfiles repo, tdm will notice and put it back.4
